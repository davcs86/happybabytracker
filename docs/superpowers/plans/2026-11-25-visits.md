# Medical Visits Implementation Plan (plan 9)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status: written 2026-11-25 against `main` 646f1c6; owner rulings below; building on branch `ccr-406c8e35-e8hvag`.
API Tasks 1–8 built (see "As built, API" below); UI Tasks 10–15 wait on the page spec's approval.**
The UI tasks (10–15) start only after the owner approves `docs/plans/ui-redesign/pages/visits.md`.

**Goal:** A visit to a doctor becomes a record of its own: scheduled or logged, editable, cancellable, with
post-visit notes, one atomic "after the visit" form that writes Growth, Vaccination and Medication rows linked
to it, an `.ics` download, and a place in Home, Timeline and the PDF export.

**Architecture:** Migration 0008 adds `visits`, a `visit_id` link on three tables and rebuilds `kid_modules`
for the new module id. The three module create functions gain a variant that takes an open `*sql.Tx` and a
visit id, so the outcome route writes every row in one SQLite transaction, re-validated by the modules' own
`mergeOnto` validators. A new stdlib-only package `api/internal/ics` writes the calendar file; the UI passes it
through unread as it does the PDF. The UI adds a Visits page, a visit page and three sheet form pages built on
the existing field sets.

**Tech Stack:** Go 1.27 (stdlib), SQLite via `modernc.org/sqlite`; SvelteKit / Svelte 5 runes, Tailwind 4,
shadcn-svelte parts. No new Go or npm dependency.

**Spec:** `docs/superpowers/specs/2026-11-25-medical-visits-design.md` sections 5–9, 11, 12 ("the visits spec";
"main N" is `2026-11-20-happybabytracker-design.md`). UI: `docs/plans/ui-redesign/pages/visits.md` (draft for
owner approval), `AGENTS.md`, `docs/plans/ui-redesign/IMPLEMENTATION.md` section 5.

## Builder rulings (this plan; open to owner correction)

- **B1.** `GET …/visits` takes `order=asc|desc` (default `desc`, any other value 422 `order`). Tracker paging is
  newest first only (`store/entries.go` `pageTail`); with it the first page of the upcoming window would hold
  the furthest visits. The UI reads Upcoming with `from=now&order=asc` and Past with `to=now` (desc). The
  cursor encodes the same `(starts_at, id)` pair in both orders. Recorded in the visits spec 5.4.
- **B2.** The `has_outcome` and `not_past` checks run inside the store transaction that makes the change, never
  as a handler pre-check (the same reasoning as CLAUDE.md rule 4): a concurrent outcome cannot slip between
  check and write.
- **B3.** The outcome's three counts are logged as three new fields on the request's one log line
  (`statusRecorder`, as `cause` and `slide` are), with names in `constants.go`.
- **B4.** The four field components gain an optional `prefix` prop (default `''`) that prefixes every `name`
  and `id`; their existing callers are unchanged. Without it two blocks in one form collide on `note`, `id`
  and the vaccine checkboxes.

## As built, API (2026-11-25)

Where the build departs from the task texts below, this list wins.
- **The module id moved to Task 8.** Adding `visits` to `model.Modules` in Task 1 breaks the export pins
  (`ExportModules == model.Modules`, one section per module) before Task 8 has a section, so Task 1 ships the schema
  (the `kid_modules` CHECK already accepts `visits`), the model and the `visit_id` columns, and Task 8 adds the id,
  `DefaultEnabled`, `ExportModules` and their pins.
- **Task 8 is pushed only together with Task 10.** The UI's `toModuleState`, `toHomeDue` and `toTimelineItem`
  throw on a value they do not know, so an API that sends `visits`, a `visit` due entry or a `visit` timeline row
  breaks the deployed UI and smoke.
- `store.VisitOutcome`, not `Outcome` (that is the reminder sender's type).
- `UpdateVisit(ctx, kidID, actorID, id, now, edit func(model.Visit) (model.Visit, error))`: PATCH merges on the
  row read inside the write transaction (the timers' `patchInTx` shape), so a PATCH of one field can never write
  back stale `outcome_notes` over notes an outcome saved meanwhile.
- `Visit(ctx, kidID, id) (VisitDetail, error)`; `VisitDetail{model.Visit; Links VisitLinks}` with
  `LinkedGrowth{ID, MeasuredOn}`, `LinkedVaccination{ID, GivenOn, Antigens}`, `LinkedMedication{ID, Name, DoseCount}`.
  `LinkedCounts` has the three list counts only; a course's dose count is on the detail.
- POST takes only `starts_at, duration_min, kind, provider, location, note`; `outcome_notes` and `cancelled` are
  PATCH-only (422 `unknown_field` on POST).
- Timeline: `store.TimelineFeedTypes` (= `TimelineTypes` + `visit`) feeds the route; `TimelineTypes` stays the
  trackers because the daily summaries and the export's tracker rows iterate it.
- `ics` tests hold the expected output inline, written by hand from RFC 5545, not golden files.
- Log fields of B3: `outcome_growth`, `outcome_vaccinations`, `outcome_medications`. Task 16: smoke's
  `logged_value` must strip them as it strips `status` and `duration_ms`.
- Home's window: "the seventh kid-local day from today" is read with today as day 0, so a visit counts while it
  starts before the start of the kid-local day today + 8.

## Review Focus

1. **A double tap on Save in "After the visit"** must record once: the second request carries the old `revision`
   and gets 409 `stale` with nothing written (Task 4 test `TestOutcomeSecondSubmitWritesNothing`; Task 13 e2e
   submits twice).
2. **One bad row among many** (vaccine 3 of 3 with a bad lot, a medication at the per-kid cap) rolls back the notes
   and every other row (Task 4 `TestOutcomeRollsBackOnLimit`; Task 6 `TestOutcomeFieldPaths`).
3. **A visit at 23:30 kid time near a DST change**: the kid-local date used for defaults, the Due window and the
   `.ics` filename is the kid's, not UTC's (Task 6 `TestOutcomeDefaultsUseKidDate`, Task 7 DST golden, Task 8
   `TestHomeDueVisitWindowIsKidLocal`).
4. **Editing a linked vaccination's antigens** keeps every dose row linked (Task 3
   `TestUpdateAdministrationKeepsVisitID`); deleting a visit with `keep` leaves the rows with `visit_id` NULL
   (Task 2).
5. **Module switched off**: an existing linked vaccine is still shown on the visit page, but the outcome form does
   not offer that section, and the Home due list drops visits when `visits` is off (Tasks 8, 13).
